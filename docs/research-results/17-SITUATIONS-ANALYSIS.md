## 1. Структура данных: 4 уровня иерархии

| Уровень | Файл | Кол-во ситуаций | Файлов |
|---------|------|-----------------|--------|
| Universal | `common files all models/situations-universal.json` | 764 | 1 |
| Brand | `brands/{brand}/situations.json` | 36,301 | 58 брендов |
| Model | `brands/{brand}/models/{model}/situations.json` | 415,258 | 857 моделей |
| Generation | `brands/{brand}/models/{model}/{gen}/situations.json` | 30,785 | 66 поколений |
| **ИТОГО** | | **483,108** | |

### Связь между уровнями

**Universal -> Brand:** Из 764 универсальных ситуаций, 430 ID совпадают с Chery (из 1087). Это значит:
- ~56% универсальных ситуаций наследуются в бренд (с теми же ID, теми же данными)
- Бренд добавляет ~651 уникальных ситуаций (source_type: `manual_warning` и т.д. — из руководств конкретного бренда)

**Model -> Generation:** На примере BMW X5:
- Model-level: 460 ситуаций
- E53: 635 (443 общих + 192 уникальных для E53)
- E70: 556 (443 общих + 113 уникальных для E70)
- F15: 443 (все из model-level)
- **Вывод:** Поколения наследуют ВСЕ ситуации model-level + добавляют уникальные из мануалов конкретного поколения

### Как Rule Engine должен резолвить ситуации

```
Приоритет: Generation > Model > Brand > Universal

1. Ищем по situation_id в generation-level
2. Если нет — model-level
3. Если нет — brand-level
4. Fallback — universal

Правило: более специфичный уровень ПЕРЕЗАПИСЫВАЕТ менее специфичный
(но только если ID совпадает; уникальные ситуации сохраняются на своём уровне)
```

## 9. Связь 25 базовых ситуаций и 764 универсальных

### Что такое base situations

25 базовых ситуаций в `situations_base.json` — это **агрегаторы верхнего уровня**. Каждая представляет ГРУППУ проблем:

| Priority | Base situations | Примеры |
|----------|----------------|---------|
| P0 (критические) | 5 | Тормоза, Check Engine, АКБ 12V, антифриз, масложор (implied) |
| P1 (важные) | 8 | Подвеска, КПП, зима, ТО, расход топлива, звуки, расход масла, руль |
| P2 (информационные) | 12 | Мультимедиа, коррозия, фары, TPMS, двери, запах, парктроники, ключ, страховка и т.д. |

### Как они должны соотноситься

```
Base situation = КОРЗИНА (container)
  |
  +-- Universal situations = ДЕТАЛЬНЫЕ ДИАГНОЗЫ внутри корзины
      (связь через layers)
```

**Пример:**
- Base: `engine_noise` (layers: [engine]) -> 320 universal ситуаций с layer=engine
- Это слишком много. Нужна более точная связка:
  - По `category` (engine): 255 universal
  - По `category` + ключевые слова: ~30-50 relевантных

### Рекомендация

Добавить поле `parent_base_id` в каждую universal ситуацию. Маппинг:

```json
{
  "brake_spongy": ["brakes"],          // 88 universal
  "engine_noise": ["engine"],           // 320 universal -> надо фильтровать
  "suspension_issue": ["chassis"],      // 35 universal
  "transmission_issue": ["drivetrain"], // 49 universal
  "battery_12v": ["electrical"],        // 140 universal -> надо фильтровать
  "coolant_leak": ["cooling"],          // 30 universal
  "fuel_consumption": ["fuel"],         // 43 universal
  "strange_sounds": ["chassis","engine"], // 354 universal -> accel+audio filter
  "oil_consumption": ["engine"],        // 320 -> keyword filter
}
```

Base ситуации — это **UI categories** для пользователя. Universal — это **diagnostic results**, которые Rule Engine возвращает.

## 10. Предлагаемый формат правила (Rule)

```json
{
  "rule_id": "RULE-FUEL-001",
  "version": "1.0",
  "name": "Бедная смесь: подсос воздуха",
  "description": "LTFT выше +10% на прогретом двигателе указывает на подсос воздуха",
  
  "triggers": {
    "type": "AND",
    "conditions": [
      {
        "source": "obd",
        "pid": "LTFT_BANK1",
        "operator": ">",
        "value": 10,
        "unit": "%",
        "duration_seconds": 30,
        "engine_state": "running",
        "min_coolant_temp_c": 80
      },
      {
        "source": "obd",
        "pid": "RPM",
        "operator": "between",
        "value": [600, 1200],
        "unit": "rpm",
        "comment": "на холостых"
      }
    ]
  },
  
  "confidence": 0.7,
  "severity": "warning",
  "urgency": 4,
  "canDrive": "limited",
  
  "situation_ids": ["yt_c5214a85", "yt_a63115ce"],
  "base_situation_id": "fuel_consumption",
  "dtc_codes_associated": ["P0171", "P0174"],
  
  "diagnosis": {
    "primary": "Подсос воздуха во впускном коллекторе",
    "secondary": ["Загрязнение ДМРВ", "Слабый топливный насос", "Загрязнённые форсунки"],
    "action": "Проверить вакуумные шланги, прокладки впускного коллектора, уплотнения дроссельной заслонки",
    "price_range": "3000-25000 руб",
    "common_mistakes": [
      "Замена форсунок без проверки давления",
      "Игнорирование коррекций более ±15%"
    ]
  },
  
  "data_requirements": {
    "obd_pids": ["LTFT_BANK1", "STFT_BANK1", "RPM", "COOLANT_TEMP"],
    "accelerometer": false,
    "audio": false,
    "min_data_duration_sec": 60
  },
  
  "hierarchy_override": {
    "brand": null,
    "model": null,
    "generation": null,
    "comment": "Если есть brand/model override, rule_id сохраняется, но triggers и diagnosis могут отличаться"
  },
  
  "metadata": {
    "source_facts": [
      "LTFT более ±10% указывает на подсос воздуха",
      "STFT скачки ±20% при стабильных оборотах — лямбда-зонд или негерметичность"
    ],
    "merged_count": 4,
    "created": "2026-04-07",
    "confidence_basis": "YouTube expert consensus (4 sources)"
  }
}
```

### Ключевые поля формата

| Поле | Назначение |
|------|-----------|
| `triggers` | Условия активации — что проверять (OBD PIDs, акселерометр, аудио, DTC) |
| `triggers.conditions[].duration_seconds` | Как долго условие должно выполняться (защита от spike) |
| `triggers.conditions[].engine_state` | Контекст: двигатель работает/заглушен/прогрев |
| `triggers.conditions[].min_coolant_temp_c` | Минимальная температура ОЖ для валидного замера |
| `confidence` | 0.0-1.0, зависит от количества источников и точности порогов |
| `situation_ids` | Связь с 764 universal ситуациями (для получения quickAnswer, facts) |
| `base_situation_id` | Связь с 25 базовыми (для UI категоризации) |
| `dtc_codes_associated` | DTC, которые подтверждают/усиливают этот диагноз |
| `hierarchy_override` | Возможность переопределения на уровне brand/model/generation |
| `data_requirements` | Какие данные нужны для правила — помогает UI показать "недостаточно данных" |

### Типы триггеров

```
1. DTC_PRESENT — наличие конкретного DTC кода
2. PID_THRESHOLD — значение PID выше/ниже порога
3. PID_RATE_OF_CHANGE — скорость изменения PID
4. ACCEL_PATTERN — паттерн вибрации (удар, дрожание, биение)
5. AUDIO_PATTERN — паттерн звука (скрип, стук, свист, гул)
6. CORRELATION — корреляция между двумя параметрами
7. TIME_CONDITION — сезон, время суток, длительность поездки
```

## 11. Стратегия заполнения DTC-маппинга

### Проблема
758 из 764 ситуаций не имеют DTC-кодов в поле dtc_codes. Но у нас есть 36K DTC кодов в dtc-universal.json.

### Решение: трёхэтапный маппинг

**Этап 1: Извлечение из текста (автоматический)**
- 31 ситуация уже содержит DTC в тексте facts/quickAnswer
- Парсить regex `P[0-9]{4}|C[0-9]{4}|U[0-9]{4}|B[0-9]{4}`
- Результат: ~37 ситуаций с DTC

**Этап 2: Семантический маппинг (полуавтоматический)**
- Для каждого DTC из 36K базы: title и description содержат ключевые слова
- Для каждой ситуации: title и facts содержат ключевые слова
- Матчинг по пересечению ключевых слов + category/layers
- Оценка: покроет ~300-400 ситуаций

**Этап 3: Экспертная верификация (ручной)**
- Для оставшихся ~350 ситуаций — часть не привязывается к DTC (визуальный осмотр, общие советы)
- Часть требует экспертного маппинга (сложные составные проблемы)

### Целевые метрики

| Источник | DTC на ситуацию | Покрытие |
|----------|-----------------|----------|
| Из текста | 1-2 | 37 ситуаций |
| Семантический | 2-5 | ~350 ситуаций |
| Экспертный | 1-10 | ~100 ситуаций |
| Не применимо | 0 | ~84 ситуации (советы, осмотр) |
| Итого DTC mapped | | ~680 из 764 (89%) |

## 12. Резюме и рекомендации

### Что уже есть
- 764 универсальные ситуации с детальными описаниями, urgency, canDrive, priceRange
- 94% ситуаций упоминают OBD-II параметры
- 50% содержат конкретные числовые пороги
- 63% связаны со звуковыми симптомами
- 4-уровневая иерархия (universal -> brand -> model -> generation) с ~483K ситуаций

### Что критически нужно
1. **DTC маппинг** — заполнить dtc_codes для 758 ситуаций без кодов
2. **Извлечение порогов** — из 382 ситуаций с числами создать конкретные условия triggers
3. **Parent mapping** — привязать 764 universal к 25 base через parent_base_id
4. **Audio/Accel signatures** — для 480 звуковых и 245 вибрационных ситуаций нужны эталонные паттерны

### Порядок реализации

```
Фаза 1 (MVP): 20 правил из Волны 1
  - Только OBD-II данные
  - LTFT/STFT пороги, coolant temp, RPM, voltage
  - Покрытие: ~5-7% ситуаций, но самые важные

Фаза 2: 50 правил (OBD + DTC)
  - DTC маппинг через семантический анализ
  - Корреляции между DTC и PID значениями
  - Покрытие: ~20% ситуаций

Фаза 3: 150 правил (+ Audio + Accel)
  - Audio pattern recognition (скрип, стук, свист)
```
