## 1. VIN через OBD (Mode 09 PID 02)

### 1.1. Команды для чтения VIN

**Последовательность через ELM327:**

```
ATZ          # Сброс адаптера
ATE0         # Выключить эхо
ATL0         # Выключить переносы строк
ATS0         # Выключить пробелы в ответах
ATH1         # Включить заголовки CAN (ВАЖНО для мульти-фрейм)
ATSP6        # Протокол CAN 11-bit 500 kbps (ISO 15765-4)
0902         # Запрос VIN (Service 09, PID 02)
```

**Альтернативный способ (AT команда):**
```
AT@1         # Возвращает "описание устройства" — НЕ VIN автомобиля!
```
> AT@1 — это описание ELM327, а не VIN. Никогда не путать.

### 1.2. Формат ответа

VIN — это 17 символов ASCII. По ISO-TP (ISO 15765-2) ответ не помещается в один CAN-фрейм (максимум 7 байт данных), поэтому используется **мульти-фреймовая передача**.

**Структура ответа на CAN шине:**

```
Запрос:  7DF 02 09 02              (функциональный адрес, 2 байта, сервис 09, PID 02)

Ответ (3 CAN-фрейма от ECU 7E8):

Фрейм 1 (First Frame):
7E8 10 14 49 02 01 4C 53 34   
│    │  │  │  │  │  └─────── VIN байты 1-3: "LS4" (hex: 4C 53 34)
│    │  │  │  │  └────────── Кол-во элементов данных: 01
│    │  │  │  └───────────── PID: 02
│    │  │  └──────────────── Service Response: 49 (= 09 + 40)
│    │  └─────────────────── Total Length: 0x14 = 20 байт (1 count + 2 header + 17 VIN)
│    └────────────────────── PCI: 10 = First Frame
└─────────────────────────── ECU Address: 7E8

Фрейм 2 (Consecutive Frame):
7E8 21 41 53 44 47 47 48 35
│    │  └──────────────────── VIN байты 4-10: "ASDGGH5"
│    └─────────────────────── PCI: 21 = Consecutive Frame #1
└──────────────────────────── ECU Address: 7E8

Фрейм 3 (Consecutive Frame):
7E8 22 36 33 31 30 30 30 31
│    │  └──────────────────── VIN байты 11-17: "6310001"
│    └─────────────────────── PCI: 22 = Consecutive Frame #2
└──────────────────────────── ECU Address: 7E8
```

**Через ELM327 (ATH1, ATS0):**
```
TX: 0902
RX: 7E810144902014C5334
    7E821415344474748
    7E82235363331303030 31
    >
```

**Через ELM327 (без заголовков ATH0):**
```
TX: 0902
RX: 014
    0: 49 02 01 4C 53 34
    1: 41 53 44 47 47 48 35
    2: 36 33 31 30 30 30 31
    >
```

### 1.3. Парсинг VIN из ответа ELM327

**Алгоритм (с заголовками ATH1, без пробелов ATS0):**

1. Собрать все фреймы в буфер
2. Найти First Frame (PCI начинается с `1`): извлечь CAN ID, длину, `4902`, байт счетчика
3. Пропустить заголовок First Frame: `[CAN_ID 3][PCI 2][LEN 2][4902 4][COUNT 2]` = 13 hex символов
4. Собрать данные из Consecutive Frames (пропуская `[CAN_ID 3][PCI 2]` = 5 hex символов)
5. Взять первые 34 hex символа = 17 байт ASCII
6. Конвертировать HEX -> ASCII

**Валидация VIN:**
- Длина = ровно 17 символов
- Допустимые символы: `A-Z`, `0-9` (кроме `I`, `O`, `Q`)
- Позиция 9 — контрольная цифра (по ISO 3779, для US-рынка обязательна)
- Позиции 1-3 — WMI (World Manufacturer Identifier)

### 1.4. Поддержка Mode 09 в различных автомобилях

**Обязательная поддержка по стандартам:**

| Регион | Стандарт | Mode 09 обязателен с |
|--------|----------|---------------------|
| США/Канада | OBD-II (CARB/EPA) | **2005+ (MY2005)** — VIN обязателен |
| Европа | EOBD (Euro 3+) | **2001+ бензин, 2004+ дизель** — VIN опционален |
| Европа | Euro 5/6 | **2009+** — VIN рекомендован, но НЕ обязателен |
| Китай | GB 18352 (China 5/6) | **2017+** — VIN рекомендован |

**ВАЖНО:** Стандарт EOBD (европейский OBD) НЕ требует поддержки Mode 09. Только EPA/CARB (американский OBD-II) требует VIN через Mode 09 PID 02 с MY2005+.

### 1.5. Китайские автомобили и Mode 09

**Li Auto (Lixiang, наш основной автомобиль):**
- LEEA 2.0 платформа, CAN 500kbps
- Отвечает на Mode 01 (текущие данные) — подтверждено логами: 7 ECU (7E8-7EF)
- **Mode 09 PID 02 (VIN) — в логах LLCAR v1.04 НЕТ записей о попытках чтения VIN с Li Auto**
- По спецификации China 6: VIN через Mode 09 рекомендован, но не все ECU реализуют
- Li Auto использует DoIP (ISO 13400) для диагностики, OBD-II — минимальный набор

**Haval / Great Wall:**
- GWM H6, Jolion, Dargo — используют CAN 500kbps
- China 6 compliant — Mode 09 обычно поддерживается
- VIN через 0902 — работает на большинстве моделей 2020+

**Chery / Exeed:**
- Tiggo 7/8, Arrizo — CAN 500kbps
- VIN через 0902 — работает на China 6 моделях

**Geely / Volvo-платформа:**
- CMA платформа (Atlas, Coolray) — полная поддержка OBD-II включая Mode 09
- SPA платформа — работает

**Общее правило для китайских автомобилей:**
> Mode 09 PID 02 (VIN) работает на ~80% автомобилей 2018+.
> Оставшиеся 20% — как правило электромобили (BEV), которые могут не иметь "основного" ECU с VIN, или старые модели на China 4/5.

### 1.6. Частые проблемы при чтении VIN

| Проблема | Причина | Решение |
|----------|---------|---------|
| `NO DATA` | ECU не поддерживает Mode 09 | Fallback: ручной ввод VIN |
| `7F 09 12` (SubFunction Not Supported) | PID 02 не реализован | Попробовать PID 00 (supported PIDs for Mode 09) |
| Неполный VIN (< 17 символов) | Потеря consecutive frames | Увеличить таймаут, повторить 2-3 раза |
| `UNABLE TO CONNECT` | Неверный протокол | Попробовать ATSP0 (авто-детект) |
| `CAN ERROR` | Адаптер потерял синхронизацию | ATZ + повторная инициализация |
| Несколько ECU отвечают | Несколько ECU имеют VIN | Брать ответ от 7E8 (primary ECU) |
| Мусор в VIN | Клон ELM327 теряет байты | Проверять ASCII валидность каждого символа |

## 2. Другие PID идентификации (Mode 09)

### 2.1. PID 00 — Supported Mode 09 PIDs

```
TX: 0900
RX: 49 00 [4 байта битмаска]
```

Битмаска показывает какие PID из 01-20 поддерживаются. **Всегда читать первым** перед запросом других Mode 09 PID.

Пример: `49 00 55 40 00 00` означает:
- PID 01: да (VIN message count)
- PID 02: да (VIN)
- PID 04: да (Calibration ID)
- PID 06: да (CVN)

### 2.2. PID 04 — Calibration ID (ECU Software Version)

```
TX: 0904
RX: 49 04 [count] [16 ASCII символов на каждый ID]
```

- Мульти-фреймовый ответ (16 байт = 32 hex на один ID)
- Может быть несколько Calibration ID (count > 1)
- **Применение в LLCAR:** определение версии прошивки ECU, обнаружение чип-тюнинга

**Пример:**
```
Calibration ID: "BOSCH_ME17_V123 " (16 символов, с пробелами до 16)
```

Уже есть в `pids.csv` LLCAR (строки 386-389):
```
0x09  0x04  calibration_identifier   ASCII
0x09  0x04  calibration_identifier2  ASCII (второй ID)
```

### 2.3. PID 06 — CVN (Calibration Verification Number)

```
TX: 0906
RX: 49 06 [count] [4 байта CVN]
```

- 4 байта (32-бит хеш прошивки), отображается как HEX
- Изменение CVN = изменение калибровки ECU (чип-тюнинг, перепрошивка)
- **Применение в LLCAR:** отслеживание изменений прошивки, сравнение с заводским CVN

Уже есть в `pids.csv` LLCAR (строка 391):
```
0x09  0x06  calibration_verification  INTEGER  0x%08x
```

### 2.4. PID 0A — ECU Name

```
TX: 090A
RX: 49 0A [count] [20 ASCII символов]
```

- 20 байт ASCII — полное имя ECU
- **Применение в LLCAR:** отображение имени ECU в диагностике, логирование

Уже есть в `pids.csv` LLCAR (строка 414):
```
0x09  0x0A  ecu_name  ASCII  20 байт
```

### 2.5. PID 08 — In-use Performance Tracking (IPT)

```
TX: 0908
RX: 49 08 [40 байт данных мониторов]
```

- Счетчики завершения мониторов (катализатор, O2, EGR и т.д.)
- Уже полностью описан в `pids.csv` LLCAR (строки 393-432)
- **Применение в LLCAR:** оценка здоровья катализатора, прогноз проблем

### 2.6. Mode 01 PID 51 — Fuel Type

```
TX: 0151
RX: 41 51 [1 байт код типа топлива]
```

**Коды типов топлива (SAE J1979):**

| Код | Топливо |
|-----|---------|
| 0x00 | Not available |
| 0x01 | Gasoline (бензин) |
| 0x02 | Methanol |
| 0x03 | Ethanol |
| 0x04 | Diesel |
| 0x05 | LPG (пропан-бутан / ГБО) |
| 0x06 | CNG (метан) |
| 0x07 | Propane |
| 0x08 | Electric (электро) |
| 0x09 | Bifuel Gasoline |
| 0x0A | Bifuel Methanol |
| 0x0B | Bifuel Ethanol |
| 0x0C | Bifuel LPG |
| 0x0D | Bifuel CNG |
| 0x0E | Bifuel Propane |
| 0x0F | Bifuel Electric |
| 0x10 | Bifuel Electric/Combustion |
| 0x11 | Hybrid Gasoline |
| 0x12 | Hybrid Ethanol |
| 0x13 | Hybrid Diesel |
| 0x14 | Hybrid Electric |
| 0x15 | Hybrid Mixed |
| 0x16 | Hybrid Regenerative |
| 0x17 | Bifuel Diesel |

**Li Auto L7 показывает PID 51 = 0x11 (Hybrid Gasoline)** — подтверждено: PID 0x51 обнаружен в `pids_discovered.txt` для Li Auto.

Уже есть в `pids.csv` LLCAR (строка 132):
```

```

### 2.7. Mode 01 PID 5B — Hybrid Battery Pack Remaining Life

```
TX: 015B
RX: 41 5B [1 байт, % = A * 100/255]
```

- Обнаружен на Li Auto (см. `pids_discovered.txt` строка 50)
- **Применение:** определение гибрида, оценка состояния батареи

### 2.8. Mode 01 PID 1C — OBD Standards

```
TX: 011C
RX: 41 1C [1 байт код стандарта]
```

| Код | Стандарт |
|-----|----------|
| 0x01 | OBD-II (CARB) |
| 0x02 | OBD (EPA) |
| 0x03 | OBD + OBD-II |
| 0x06 | EOBD |
| 0x07 | EOBD + OBD-II |
| 0x0D | JOBD (Япония) |
| 0x11 | China OBD |
| 0x13 | KOBD (Корея) |

- Обнаружен на Li Auto
- **Применение:** определение региона автомобиля, понимание какие PID должны поддерживаться

### 2.9. Что НЕЛЬЗЯ определить через стандартный OBD

| Параметр | Доступность |
|----------|-------------|
| Объем двигателя | **НЕТ** — нет стандартного PID |
| Количество цилиндров | **Косвенно** — по наличию Bank 2 (PID 08/09 vs нет = 4 цил / V6+V8) |
| Тип привода (AWD/FWD/RWD) | **НЕТ** |
| КПП (МКПП/АКПП) | **Косвенно** — PID 0x0D скорость vs PID 0x0C обороты = передаточное число |
| Мощность двигателя | **Частично** — PID 0x63 Reference Torque (Нм), обнаружен на Li Auto |
| Пробег | **ДА** — PID 0xA6 Odometer (обнаружен на Li Auto), также PID 0x9D Service Data |

## 3. Анализ кода LLCAR v1.04

### 3.1. Что уже реализовано

**VIN чтение — ДА, реализовано полностью:**

| Файл | Описание |
|------|----------|
| `Services/IBluetoothOBD2Service.cs:106` | Интерфейс: `Task<string?> ReadVinAsync(CancellationToken ct)` |
| `Services/AndroidBluetoothOBD2Service.cs:1582-1642` | Полная реализация для Android (BLE + Classic BT) |
| `Services/IOSBluetoothOBD2Service.cs:827-873` | Реализация для iOS |
| `Services/BackgroundDataService.cs:390-483` | Автоматическое чтение VIN при подключении |
| `Models/SettingsData.cs:117-121` | Хранение VIN в настройках |
| `PageModels/SettingsPageModel.cs:70` | Отображение VIN в UI |

**Как работает VIN в LLCAR v1.04:**

1. `BackgroundDataService.InitializeAsync()` проверяет `settings.Vin`
2. Если VIN пуст — вызывает `ReadVinAsync()` (до 2 попыток, таймаут 3 сек на попытку)
3. VIN сохраняется в `SettingsData.Vin`
4. Из VIN вычисляется `ClientHash` для идентификации на сервере
5. При неудаче — событие `VinReadFailed` с сообщением для UI

**Парсинг VIN (Android):**
- `ParseVinFromResponse()` (строки 2048-2174) — разбирает мульти-фреймовый ISO-TP ответ
- Обрабатывает CAN ID: 7E8, 7E0, 7E1, 7E9
- Извлекает данные из First Frame (пропуск 8 hex заголовка) и Consecutive Frames
- Конвертация HEX -> ASCII через `HexToAscii()` (строки 2176-2214)
- Валидация: ровно 17 символов, только alphanumeric

**Парсинг VIN (iOS) — упрощенный:**
- Ищет подстроку "4902" в ответе
- Берет следующие 34 hex символа = 17 ASCII символов VIN
- **Проблема:** не обрабатывает мульти-фрейм корректно, может сломаться

### 3.2. Проблемы в текущей реализации

**1. Android: жестко зашитые CAN ID**
```csharp
// Строка 2072-2073
if (response.Substring(searchPos, 3) == "7E8" || response.Substring(searchPos, 3) == "7E0" ||
    response.Substring(searchPos, 3) == "7E1" || response.Substring(searchPos, 3) == "7E9")
```
- Не обрабатывает 7EA-7EF (а Li Auto отвечает с 7EA, 7EB, 7EC, 7ED, 7EE, 7EF!)
- VIN обычно приходит от 7E8 (primary ECU), но китайские авто могут отвечать с другого

**2. ecu_mask=1 для VIN — правильно**
```csharp
// Строка 1606
var result = await SendCommandWithMultiFrameSupportAsync(cmd, 0x01, ct);
```
- `0x01` = ожидаем ответ только от 7E8 — это корректно для VIN

**3. iOS реализация хрупкая**
- Нет мульти-фрейм парсинга
- Простой поиск "4902" может найти совпадение в данных

**4. Нет проверки Mode 09 поддержки**
- Не отправляется `0900` перед `0902`
- Если ECU не поддерживает Mode 09, тратятся 2 попытки x 3 секунды = 6 секунд впустую

**5. Нет Mode 09 в других целях**
- Calibration ID (0904), CVN (0906), ECU Name (090A) — описаны в pids.csv, но **не запрашиваются** в коде
- Можно добавить чтение при подключении рядом с VIN

### 3.3. Что НЕ реализовано, но описано в pids.csv

Все PID из Mode 09 уже описаны в `pids.csv` (строки 383-432), но код их не запрашивает:

| 09 02 | VIN | **Читается** |
| 09 03 | Cal ID message count | Описан, не читается |

| 09 05 | CVN message count | Описан, не читается |
| 09 06 | CVN | Описан, не читается |

| 09 08 | IPT (20 пар счетчиков) | Описан, не читается |
| 09 09 | ECU name length | Описан, не читается |

## 4. Совместимость ELM327

### 4.1. ELM327 v1.5 vs v2.1

| Функция | v1.0-v1.4 | v1.5 | v2.1 |
|---------|-----------|------|------|
| Mode 09 (VIN) | Да | Да | Да |
| ISO-TP multi-frame | Да | Да | Да |
| CAN 500k | Да | Да | Да |
| CAN 250k | Да | Да | Да |
| Flow Control | Авто | Авто | Авто |
| STN расширения | Нет | Нет | Нет |
| Макс. фреймов | 7+ | 7+ | 7+ |

**Вывод: для VIN нет разницы между v1.5 и v2.1.** Мульти-фреймовый ответ VIN (3 фрейма) работает на всех версиях ELM327.

### 4.2. Китайские клоны ELM327

**Реальность рынка:** ~95% адаптеров на AliExpress/Wildberries/Ozon — это клоны на чипах:
- **PIC18F25K80** + прошивка клона (самый распространенный)
- **STM32** + собственная прошивка (OBDLink-подобные)
- **ESP32** + WiFi (для iOS)
- **HC-05/HC-06** + PIC (Bluetooth Classic, дешевые)

**Проблемы клонов с VIN чтением:**

| Проблема | Частота | Описание |
|----------|---------|----------|
| Потеря Consecutive Frames | ~15% клонов | Адаптер теряет 2-й или 3-й фрейм ISO-TP, VIN приходит неполным |
| Медленный ответ | ~30% клонов | Ответ за 500ms+ вместо 50-100ms, нужен увеличенный таймаут |
| Flow Control ошибки | ~5% клонов | Адаптер не отправляет FC фрейм, ECU не продолжает передачу |
| ATH1 не работает | ~3% клонов | Заголовки не включаются, парсинг ломается |
| Фейковая версия | ~80% | Сообщают "ELM327 v2.1" а реально v1.0 — на VIN не влияет |

**Рекомендации для надежного чтения VIN на клонах:**

1. **Таймаут 1500-3000ms** (не 200ms как для обычных PID)
2. **2-3 попытки** при неудаче (уже реализовано в LLCAR: 2 попытки)
3. **Валидировать длину** — если < 17 символов, повторить
4. **Проверять ASCII** — если содержит непечатные символы, адаптер потерял данные
5. **Flow Control вручную** — если FC не работает: `ATFCSH7E0`, `ATFCSD300000`, `ATFCSM1`

### 4.3. Bluetooth vs WiFi

| Параметр | Bluetooth Classic | BLE | WiFi |
|----------|------------------|-----|------|
| VIN чтение | Работает | Работает | Работает |
| Latency | ~15-30ms | ~30-100ms | ~5-15ms |
| Multi-frame | Стабильно | Зависит от MTU | Стабильно |
| iOS поддержка | НЕТ (MFi) | ДА | ДА |
| Потеря данных | Редко | BLE MTU может обрезать | Редко |

**BLE особенность:** MTU по умолчанию = 20 байт. Для мульти-фреймового ответа VIN (~40+ байт) нужно:
- Либо MTU negotiation до 100+
- Либо адаптер разбивает на BLE пакеты и собирает на стороне приложения

LLCAR v1.04 уже обрабатывает это через `_responseBuffer` и буферизацию в `AndroidBluetoothOBD2Service`.

## 5. Обнаружение ГБО, удаленного катализатора, чип-тюнинга

### 5.1. Обнаружение ГБО (LPG/CNG)

**Прямое обнаружение:**
- **PID 0x51 (Fuel Type):** если ECU сообщает 0x05 (LPG), 0x06 (CNG), 0x09-0x17 (bifuel/hybrid) — ГБО установлено штатно или ECU перепрограммирован
- **Проблема:** 99% установок ГБО в России — это **параллельные системы** с отдельным ECU. Штатный ECU продолжает сообщать 0x01 (Gasoline). ГБО-контроллер (Stag, Lovato, OMVL) **не виден через OBD-II** стандартный порт

**Косвенные признаки ГБО:**

| Признак | PID | Как определить |
|---------|-----|---------------|
| Нестабильный STFT | 0x06 | STFT прыгает при переключении бензин/газ (±10-20%) |
| Повышенный LTFT | 0x07 | LTFT > +10% при работе на газе (газ беднее) |
| Lambda != 1.0 | 0x24 | Колебания Lambda при переключении топлива |
| Несоответствие MAP/RPM | 0x0B/0x0C | При работе на газе MAP может отличаться |
| Доп. ECU на шине | 7E9-7EF | Некоторые ГБО-контроллеры (Stag 4+) подключаются к CAN |

**Вывод:** Надежно определить ГБО через стандартный OBD-II **невозможно**. Можно только:
1. Проверить PID 0x51 (работает только если ECU перепрошит)
2. Анализировать паттерн STFT/LTFT (косвенно, с ложными срабатываниями)
3. Спрашивать пользователя при регистрации

### 5.2. Обнаружение удаленного катализатора

**Прямое обнаружение через OBD-II:**

| Метод | PID / Mode | Описание |
|-------|-----------|----------|
| Readiness Monitor | 01 01 (бит Catalyst) | Если Catalyst monitor "not ready" или "not supported" — катализатор может быть удален |
| P0420/P0430 DTC | Mode 03 | Ошибка эффективности катализатора — если удален без прошивки |
| O2 Sensor Post-cat | 01 15 (B1S2) | Если сигнал post-cat O2 повторяет pre-cat (01 14 B1S1) — катализатор пустой |
| Catalyst Temperature | 01 3C | Нет нагрева катализатора (< 200°C на прогретом двигателе) |
| IPT (Mode 09 PID 08) | CATCOMP1/CATCOND1 | Счетчик мониторинга катализатора не увеличивается |

**Алгоритм определения удаленного катализатора:**

```
1. Проверить Readiness (PID 0x01):
   - Catalyst monitor = "not supported" -> ПОДОЗРИТЕЛЬНО (удален + прошит)
   - Catalyst monitor = "not complete" после 1000+ км -> ПОДОЗРИТЕЛЬНО

2. Сравнить O2 сенсоры:
   - Pre-cat O2 (PID 0x14, B1S1) vs Post-cat O2 (PID 0x15, B1S2)
   - Если амплитуды совпадают (корреляция > 0.8) -> КАТАЛИЗАТОР УДАЛЕН
   - Если post-cat O2 показывает стабильные ~0.45V -> КАТАЛИЗАТОР РАБОТАЕТ

3. Проверить P0420/P0430 в DTC:
   - Если код есть -> катализатор удален, но ECU не перепрошит
   - Если кода нет + мониторы "not supported" -> удален И прошит

4. Catalyst Temperature (PID 0x3C):
   - На прогретом двигателе < 300°C -> ПОДОЗРИТЕЛЬНО
   - Нормальная температура катализатора: 400-800°C
```

**Li Auto L7 специфика:**
- PID 0x3C (Catalyst Temperature B1S1) — обнаружен в `pids_discovered.txt`
- PID 0x14 (O2 B1S1) — НЕ обнаружен (Li Auto использует wideband, PID 0x34)
- PID 0x15 (O2 B1S2) — обнаружен
- **Особенность PHEV:** при работе на электротяге катализатор холодный — это нормально

### 5.3. Обнаружение чип-тюнинга

**Через OBD-II:**

| Метод | Данные | Как определить |
|-------|--------|---------------|
| Calibration ID | Mode 09 PID 04 | Сравнить с заводским ID для данного VIN/модели |
| CVN | Mode 09 PID 06 | Изменение CVN = изменение прошивки |
| Readiness monitors | PID 01 01 | Отключенные мониторы = перепрошивка |
| Boost pressure | PID 0x6F | Давление наддува выше заводского = stage тюнинг |
| Reference Torque | PID 0x63 | Не меняется (зашит в ECU), но можно сравнить с базой |

**Практический алгоритм:**

```
1. Прочитать CalID (0904) и CVN (0906)
2. Запросить у сервера заводские CalID/CVN для данного VIN
3. Если не совпадают -> ECU перепрошит
4. Проверить readiness monitors:
   - Если ключевые мониторы "not supported" -> эмиссия отключена
5. При наличии наддува: сравнить boost pressure с заводскими лимитами
```

**Ограничения:**
- Нужна база заводских CalID/CVN для каждой модели/года — сложно собрать
- Некоторые stage-тюнеры восстанавливают CVN = не обнаруживается
- Только для ECU engine — другие ECU не меняются

## 6. Рекомендации для LLCAR

### 6.1. Немедленные улучшения (текущий VIN код)

**1. Добавить проверку поддержки Mode 09:**
```csharp
// Перед 0902, отправить 0900 для проверки
var supported = await SendCommandAsync("0900", ct);
if (supported.Contains("4900"))
{
    // Парсить битмаску: бит 1 = PID 02 (VIN) поддерживается
    var mask = ParseSupportedPids(supported);
    if (mask.Contains(0x02))
    {
        vin = await ReadVinAsync(ct);
    }
}
```

**2. Исправить жесткие CAN ID в ParseVinFromResponse:**
```csharp
// Вместо:
if (response.Substring(searchPos, 3) == "7E8" || ...)

// Использовать:
if (response.Length >= searchPos + 3 &&
    response.Substring(searchPos, 2) == "7E" &&
    IsHexDigit(response[searchPos + 2]))
```

**3. Добавить VIN валидацию:**
```csharp
private bool IsValidVin(string vin)
{
    if (vin.Length != 17) return false;
    // VIN не содержит I, O, Q
    if (vin.Any(c => c == 'I' || c == 'O' || c == 'Q')) return false;
    // Только alphanumeric
    if (!vin.All(char.IsLetterOrDigit)) return false;
    return true;
}
```

### 6.2. Расширение идентификации автомобиля

**Последовательность при первом подключении:**

```
1. Подключение к ELM327
2. Инициализация (ATZ, ATE0, ATL0, ATS0, ATH1, ATSP6)
3. ECU detection (0100)
4. Проверка Mode 09 поддержки (0900)
5. Чтение VIN (0902) — если поддерживается
6. Чтение Fuel Type (0151) — определить бензин/дизель/гибрид/электро
7. Чтение OBD Standard (011C) — определить регион (OBD-II/EOBD/China OBD)
8. Чтение Calibration ID (0904) — версия прошивки ECU
9. Чтение CVN (0906) — контрольная сумма прошивки
10. Чтение ECU Name (090A) — имя ECU
11. Чтение Hybrid Battery (015B) — если гибрид
12. Чтение Reference Torque (0163) — крутящий момент для профиля двигателя
13. Чтение Odometer (01A6) — текущий пробег
```

**Общее время: ~3-5 секунд** (с учетом мульти-фреймов и таймаутов клонов).

### 6.3. VIN декодирование

По VIN можно определить:
- **WMI (позиции 1-3):** производитель и страна
  - Li Auto: `LCN` (Changzhou), `LSW` (Beijing)
  - Haval: `LGW`
  - Chery: `LVV`, `LWD`
  - Geely: `LBE`, `L6T`
- **VDS (позиции 4-8):** модель, кузов, двигатель
- **VIS (позиции 10-17):** год, завод, серийный номер

**Позиция 10 — год выпуска:**
```
A=2010, B=2011, C=2012, D=2013, E=2014, F=2015,
G=2016, H=2017, J=2018, K=2019, L=2020, M=2021,
N=2022, P=2023, R=2024, S=2025, T=2026, V=2027
```

> Рекомендация: после чтения VIN — автоматически определять марку/модель/год через NHTSA API (для US VIN) или собственную базу WMI.

### 6.4. Fallback при отсутствии VIN

Если Mode 09 PID 02 не поддерживается:
1. **Попробовать UDS:** `22 F190` (UDS ReadDataByIdentifier, DID F190 = VIN) — работает на многих современных ECU
2. **Сгенерировать pseudo-ID:** hash из (CalibrationID + ECU_Name + BT_Adapter_MAC)
3. **Запросить у пользователя** — ввод VIN вручную, сканирование QR/штрихкода с наклейки
