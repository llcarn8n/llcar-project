# Секция 7: Correlation Engine (accel↔audio)

**Дата:** 2026-04-07
**Статус:** утверждено Петром

---

## Назначение

Конкурентное преимущество LLCAR — ни один конкурент не связывает вибрацию со звуком. Работает только на T3 (OBD + акселерометр + аудио). Позволяет диагностировать механические проблемы, которые невозможно определить из OBD данных.

---

## Batch, не real-time

Корреляции считаются ПОСЛЕ поездки, не в реальном времени. Причины:
- Нужно минимум 50-100 точек в одном режиме (одно окно = 4.5 секунд)
- Акселерометр и аудио имеют разные временные окна — нужен join по времени с допуском ±3 секунды
- Результат стабилен в рамках поездки — нет смысла считать чаще
- Экономит батарею и процессор смартфона

Запускается как cron job на сервере после загрузки данных поездки.

---

## 5 диагностически значимых корреляций

### 1. Вибрация Z ↔ обороты двигателя (приоритет P0)

**Что выявляет:** износ опор (подушек) двигателя

**Что ищем:** линейная зависимость вибрации по вертикальной оси (az_std) от оборотов (RPM)

**Метод:** линейная регрессия az_std vs RPM по окнам одной поездки

**Срабатывание:** коэффициент корреляции r > 0.6 и наклон (slope) положительный

**Логика:** двигатель трясётся сильнее на высоких оборотах. Исправные подушки гасят эту вибрацию и она не передаётся на кузов. Если подушки изношены — вибрация проходит, и чем выше обороты, тем сильнее трясёт.

---

### 2. Частота звука ↔ скорость колеса (приоритет P0)

**Что выявляет:** износ ступичного подшипника

**Что ищем:** доминантная частота звука пропорциональна скорости вращения колеса

**Метод:** вычисляем частоту вращения колеса = speed / (3.6 × π × диаметр_колеса). Проверяем: dominant_freq / частота_колеса = целое число (гармоника). Если это отношение = const на разных скоростях — подшипник.

**Срабатывание:** отношение freq/tire_freq стабильно (дисперсия < 0.5) на 50+ окнах при разных скоростях

**Логика:** изношенный ступичный подшипник гудит с частотой, прямо пропорциональной скорости вращения колеса. На 60 км/ч гудит тихо, на 120 — громко и на более высокой частоте. Это уникальная сигнатура — ничто другое так себя не ведёт.

---

### 3. Вибрация Y + аудио-импульс при повороте (приоритет P1)

**Что выявляет:** износ ШРУСа или подшипника ступицы

**Что ищем:** совпадение по времени трёх событий:
1. Вибрация по боковой оси (ay) > 2.5 м/с²
2. Скачок (импульс) в аудио
3. Режим = поворот (cornering)

**Метод:** event detection — ищем окна где все три условия совпадают

**Срабатывание:** 3+ совпадения за поездку

**Логика:** ШРУС (шарнир равных угловых скоростей) щёлкает или хрустит при повороте на определённый угол. Одновременно ощущается вибрация в боковой плоскости. Ни подвеска, ни двигатель так себя не ведут — это уникальный паттерн.

---

### 4. Вибрация Z ↔ скорость на трассе (приоритет P1)

**Что выявляет:** дисбаланс колёс

**Что ищем:** пик вибрации az_std в узком диапазоне скоростей (например, 90-100 км/ч), при этом на других скоростях — нормально

**Метод:** группировка окон по скорости (бины по 10 км/ч), поиск бина с аномально высокой средней вибрацией

**Срабатывание:** вибрация в пиковом бине > 2× средней вибрации в соседних бинах

**Логика:** несбалансированное колесо начинает раскачиваться на определённой скорости (резонанс). При замедлении или ускорении — вибрация пропадает. Это классический признак дисбаланса, который отличается от проблем подвески (подвеска трясёт на ЛЮБОЙ скорости по плохой дороге).

---

### 5. Высокочастотный звук > 200 Гц + вибрация (приоритет P2)

**Что выявляет:** износ подшипника генератора, компрессора кондиционера или натяжителя ремня

**Что ищем:** корреляция аудио в высоком частотном диапазоне (> 200 Гц) с вибрацией, при контроле RPM

**Метод:** partial correlation — считаем связь audio↔vibration при фиксированных оборотах

**Срабатывание:** partial r > 0.5 при data_points > 50

**Логика:** изношенный подшипник навесного оборудования (генератор, компрессор, натяжитель ремня) визжит на высокой частоте и одновременно создаёт вибрацию, передающуюся на кузов. Частота зависит от RPM, но на одних и тех же оборотах — стабильна.

---

## Алгоритм работы

1. Получить данные поездки с сервера: accel_windows + audio_windows + OBD пакеты
2. Join по времени: для каждого accel_window найти ближайший audio_window (допуск ±3 секунды) и ближайший OBD пакет
3. Отфильтровать: только окна со стабильным режимом (> 10 секунд в одном режиме)
4. Для каждой из 5 корреляций:
   - Отобрать окна подходящего режима (например, "вибрация↔RPM" = все режимы, "вибрация↔скорость на трассе" = только highway)
   - Посчитать коэффициент корреляции r, наклон slope, значимость p-value
   - Проверить количество точек (минимум 50)
5. Если |r| > 0.6 и data_points > 50 → сгенерировать корреляционный факт
6. Факт уходит в Rule Engine как обычный факт — дальше обрабатывается правилами

---

## Практические ограничения

- 173K accel_windows + 85K audio_windows за 12 дней от 5 клиентов. При join по времени с tolerance — реальных пар будет значительно меньше. Нужно сначала проверить, сколько окон реально overlapping.
- Качество аудио зависит от расположения телефона (в кармане, в держателе, в бардачке) — шум салона может маскировать полезный сигнал.
- Диаметр колеса для корреляции №2 — берётся из Vehicle Profile (specs модели в vehicles-ru.json) или задаётся стандартный (0.63м).

## Хранение результатов

Таблица `correlation_results`:
- Время вычисления
- Хэш клиента
- ID поездки (или временной диапазон)
- Тип корреляции: vibration_rpm / audio_wheel / turn_click / vibration_speed_peak / highfreq_vibration
- Коэффициент корреляции r
- Наклон (slope)
- Значимость (p-value)
- Количество точек данных
- Режим при котором считалось
- Подсказка диагноза: engine_mount / wheel_bearing / cv_joint / wheel_balance / accessory_bearing
