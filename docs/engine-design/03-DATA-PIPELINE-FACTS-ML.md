## Pipeline: 5 шагов

```
Сырые данные → Нормализатор → Извлечение фич → Генерация фактов → Правила → Диагноз
```

### Шаг 1: Нормализатор

Принимает данные от приложения (OBD пакеты, акселерометр окна, аудио окна). Выполняет:

1. **Валидация** — отбрасывает физически невозможные значения:
   - RPM > 10000 или < 0
   - Coolant < -50C или > 250C
   - Voltage < 0 или > 25V
   - LTFT/STFT вне диапазона -100%...+100%
   - Невалидные записи не диагностируются — drop + лог

2. **Определение режима** — на основе speed + RPM + акселерометр + road_type:
   - idle (холостой): speed < 3 km/h или standstill
   - city (город): speed 3-70 km/h
   - highway (трасса): speed > 70 km/h
   - acceleration (разгон): ax > 2.0 m/s2
   - braking (торможение): ax < -2.0 m/s2
   - cornering (поворот): |ay| > 2.5 m/s2

3. **Контекст двигателя:**
   - Прогрет или нет: coolant > 80C = warm
   - Холодный пуск: первые 3 минуты после запуска
   - Время непрерывного движения (минуты)
   - Температура за бортом (если доступна)

4. **Определение tier:** T1/T2/T3 по наличию данных (только OBD / +акселерометр / +аудио)

### Шаг 2: Извлечение фич (Feature Extractor)

Считает производные метрики из нормализованных данных:

**Существующие (из anomaly_engine.py):**
- Общая вибрация (RMS трёх осей std)
- Crest Factor Z (пик / RMS — характеристика ударных нагрузок)
- Shape Ratio Z (std / range — форма распределения)
- Virtual Freq Source (привязка доминантной частоты к двигателю или колёсам)
- Ranges (ax/ay/az max - min)

**Новые:**
- Модуль LTFT (абсолютное значение коррекции)
- Рассогласование LTFT vs STFT (delta = ltft - stft)
- Совпадение знаков LTFT и STFT (если одинаковый знак — проблема в топливе, разный — в датчиках)
- Вибрация/скорость (отношение az_std к speed — нормализация по скорости)

### Шаг 3: Генерация фактов (Fact Generator)

Превращает числа в утверждения о состоянии. Это ключевой шаг — здесь числа становятся смыслом.

**Входы:** нормализованный пакет, извлечённые фичи, Vehicle Profile, baselines, история
**Выход:** список фактов (0 или более)

**Источники фактов:**

1. **DTC факты (T1)** — для каждого активного DTC кода: resolve через 4-level KB → severity, can_drive, title
2. **LTFT/STFT факты (T1)** — через FuelTrim Analyzer (отдельная подсистема, секция 4): severity с учётом коррекций ГБО/Евро-2/зима/платформа
3. **Пороговые факты (T1)** — coolant > 105C = перегрев, voltage < 13V при оборотах > 1000 = генератор
4. **Z-score аномалии (T2/T3)** — отклонение от персонального baseline: |z| > 2.0 = warning, |z| > 3.0 = critical
5. **Multi-DTC паттерны (T1)** — комбинации кодов: P0171+P0174 = подсос воздуха, P0300+P0301+P0302 = катушка зажигания
6. **Трендовые факты (история)** — CUSUM alarm, деградация baseline, тренд LTFT за несколько поездок
7. **Корреляционные факты (T2+T3, batch)** — вибрация↔обороты, частота↔скорость колеса

---

## Три типа фактов

### Мгновенные факты (одно наблюдение)
Генерируются из текущего пакета данных. Примеры:
- "Активен код P0171" (severity=warning, can_drive=yes_caution)
- "LTFT 12% = проблема" (с учётом коррекции: corrected=8.2%, correction=euro2)
- "Температура 108C = перегрев" (severity=danger, can_drive=no_stop)
- "Напряжение 12.1V при 1500 RPM = генератор" (severity=warning)
- "Вибрация Z: z-score 3.5 на трассе" (severity=critical)

### Трендовые факты (история за несколько поездок)
Генерируются из накопленных данных. Примеры:
- "LTFT растёт 3 дня подряд: 7% → 10% → 13%" (trend=+2%/день)
- "CUSUM alarm: подвеска деградирует" (short_term alarm)
- "Baseline drift: средняя вибрация выросла на 40% за месяц"

### Корреляционные факты (связь между датчиками)
Генерируются batch job'ом из данных поездки. Примеры:
- "Вибрация Z растёт с оборотами: r=0.82, slope=0.003" → опоры двигателя
- "Частота звука совпадает со скоростью колеса: freq/tire_freq = 4.0 (const)" → ступичный подшипник
- "P0171 + P0174 одновременно" → подсос воздуха (не инжектор)
- "Стук при повороте + вибрация Y" → ШРУС

## Состав каждого факта

Каждый факт — утверждение: "что случилось, насколько серьёзно, насколько уверены, в каком контексте".

- **Тип** — что обнаружено (перегрев, DTC, аномалия вибрации, тренд LTFT, корреляция...)
- **Серьёзность** — 4 уровня: норма (ok) / внимание (warning) / проблема (critical) / опасность (danger)
- **Уверенность** — от 0% до 100%. Зависит от количества данных в baseline (< 30 замеров = низкая, > 200 = высокая)
- **Контекст** — режим (idle/city/highway), прогрет ли двигатель, скорость, температура за бортом, холодный пуск
- **Tier источника** — T1/T2/T3 (какие датчики использовались)
- **Детали** — специфичные для типа: код DTC, значение z-score, r корреляции, сырые числа, имя baseline feature

---

## Зачем нужен слой фактов

1. **Объяснимость** — пользователю показываем: "Диагноз основан на: LTFT 12% (проблема) + код P0171 + вибрация при оборотах (r=0.8)"
2. **Логирование** — сохраняем факты → можно анализировать почему движок ошибся
3. **Тестируемость** — подаём набор фактов → проверяем что правила дают правильный диагноз
4. **Разделение ответственности** — нормализатор не знает про правила, правила не знают про сырые данные
5. **ML training** — факты = промежуточные features для будущих моделей

## ML-Ready: сбор данных для обучения

### Что записываем параллельно с pipeline

Каждый шаг pipeline ПАРАЛЛЕЛЬНО пишет данные для будущего ML:

| Что | Где | Зачем |
|-----|-----|-------|
| Features per window | anomaly_scores.features_json | Training data: вход модели |
| Факты | fact_log (новая таблица) | Labels: что движок решил |
| Обратная связь пользователя | user_feedback (новая таблица) | Ground truth: подтвердил/отклонил |
| Baselines per client | anomaly_baselines | Персонализация: "норма для этой машины" |
| Vehicle Profile | vehicle_profiles | Группировка: обучение per platform/brand |

**Критично:** features_json пишется ВСЕГДА, даже когда диагноз "норма" — это negative examples для ML.

### User Feedback (обратная связь)

На каждый диагноз — кнопки:
- "Подтверждаю" — ground truth positive
- "Не так" — false positive, вес правила снижается
- "Починил, проблема ушла" — confirmed diagnosis + resolved

Без user feedback supervised ML невозможен.

### Три этапа обучения

**Этап 1 (сейчас, 5 клиентов):** Welford baselines (unsupervised). "Норма для этой машины" → отклонение = аномалия. Веса правил — экспертные (захардкожены из YouTube, CustDev, автодиагностика).

**Этап 2 (50+ клиентов, 3-6 месяцев):** Калибровка весов и порогов на данных.
- Правило сработало 100 раз, подтверждено 80 → вес растёт
- Правило сработало 50 раз, отклонено 40 → вес падает, порог повышается
- На платформе VW MQB "вибрация Z > 3.0" ложная тревога в 60% → порог для VW MQB поднимается до 4.0
- Популяционные нормы: "Все Chery Tiggo 8 Pro на пробеге 30-50K имеют az_std=1.2 на трассе" → замена хардкодных POPULATION_PRIORS

**Этап 3 (500+ клиентов, 6-12 месяцев):** Supervised classification. "При таких фичах + таком профиле → с вероятностью 87% это подушки двигателя". Обучаем на confirmed diagnoses.

### Версионирование весов

- v1 = экспертные веса (текущие)
- v2 = откалиброванные из данных (этап 2)
- v3 = ML-выученные (этап 3)
- Откат на предыдущую версию если новая хуже
- Веса per scope: глобальные → per platform → per brand → per model (чем больше данных на уровне, тем точнее калибровка)
- A/B тестирование: новый клиент может получить v1 или v2 для сравнения точности
