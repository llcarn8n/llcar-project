# Секция 6: Rule Engine (движок правил)

**Дата:** 2026-04-07
**Статус:** утверждено Петром

---

## Два типа правил

### Простые (JSON, 100+ штук)
Пороговые проверки — "если coolant > 105°C = перегрев". Хранятся в JSON, интерпретируются движком. Обновляются без деплоя. Покрывают ~80% диагностики.

Примеры:
- Температура охлаждающей жидкости > 105°C → перегрев (severity=danger, can_drive=no)
- Напряжение < 13V при оборотах > 1000 → генератор (severity=warning)
- LTFT > 10% → проблема топливной системы (делегируется FuelTrim Analyzer)
- DTC P0300 → пропуски зажигания (severity=urgent)
- Вибрация Z: z-score > 3.0 на трассе → подвеска (severity=critical)

### Сложные (Python, ~10-15 штук)
Логика которую невозможно выразить в JSON:
- Корреляция вибрации Z с оборотами двигателя (линейная регрессия по окнам одной поездки) → опоры двигателя
- Привязка доминантной частоты звука к гармоникам двигателя или колёс → источник шума
- Совпадение частоты звука со скоростью колеса (частота / частота_вращения_колеса = const) → ступичный подшипник
- Стук при повороте + вибрация по оси Y → ШРУС
- Кросс-анализ LTFT vs STFT двух банков → тип проблемы (топливо vs датчик)

Обновляются только через деплой кода.

## Из чего состоит каждое правило

- **Имя и описание** — машинное имя (worn_suspension) + человеческое ("Износ подвески")
- **Tier** — T1 (только OBD), T2 (+акселерометр), T3 (+аудио). Определяет какие данные нужны для срабатывания.
- **Условия** — список проверок: какой факт, какой оператор (больше/меньше/z-score/в диапазоне/тренд), порог, вес условия. Условия объединяются через И/ИЛИ.
- **Контекст** — когда правило вообще применимо:
  - Режим: только на трассе, только на холостом, только в городе
  - Двигатель прогрет (coolant > 80°C)
  - Скорость > X или < Y
  - Не холодный пуск (первые 3 минуты исключены)
- **Коррекции** — модификации порогов для ГБО/Евро-2/платформы. Пример: порог LTFT для правила "бедная смесь" = 10% по умолчанию, но для ГБО = 15%, для GM = 13%.
- **Минимальная уверенность** — порог ниже которого не показываем пользователю (антиспам). Обычно 40%.
- **Cooldown** — сколько дней не показывать после отклонения пользователем. По умолчанию 7 дней.
- **Привязка к ситуации** — ID из situations-universal.json → quickAnswer, маршрутная карта, цена ремонта, canDrive
- **Привязка к DTC** — какие коды ошибок связаны с этим правилом. При наличии DTC из списка — boost уверенности.

## Как считается уверенность (confidence)

Три компонента, в сумме 0-100%:

### 1. Совпадение условий (40% от итога)
Сколько условий выполнено, с учётом весов. Если правило имеет 5 условий с весами 3+2+2+1+3 = 11, и выполнены условия с весами 3+2+3 = 8, то match_score = (8/11) × 40 = 29%.

### 2. Степень отклонения (40% от итога)
Насколько сильно превышен порог. Пример: порог coolant = 105°C.
- Факт: 106°C → едва превышен → deviation_score низкий
- Факт: 120°C → в 1.5 раза выше порога → deviation_score высокий

### 3. Повторяемость (20% от итога)
Сколько раз подряд правило сработало в последовательных замерах.
- 1 раз = возможно шум → persistence_score = 4%
- 3 раза = заслуживает внимания → persistence_score = 12%
- 5+ раз = стабильная проблема → persistence_score = 20% (максимум)

## Статусы диагноза

| Уверенность | Статус | Что показываем пользователю |
|------------|--------|----------------------------|
| 70-100% | ВЕРОЯТНО | Полный диагноз + маршрутная карта ремонта + цена |
| 40-69% | ВОЗМОЖНО | Предупреждение + "стоит проверить при случае" |
| 1-39% | МАЛОВЕРОЯТНО | Не показываем в приложении. Видно только в расширенном режиме дашборда. |
| 0% | ЧИСТО | Ничего не показываем |

## Защита от ложных срабатываний

Ложные срабатывания — проблема №1. Каждый false positive снижает доверие к системе.

### 1. Cooldown per rule per client
Пользователь отклонил диагноз ("не так") → не показываем это правило 7 дней. После 7 дней — если проблема осталась, покажем снова. Хранится в таблице diagnostic_persistence.

### 2. Минимальное количество срабатываний
Правило должно сработать минимум 3 раза подряд прежде чем показать пользователю. Одно срабатывание = шум, три = паттерн.

### 3. Фильтр стабильности режима
Не диагностируем в переходных режимах. Если за последние 5 секунд режим менялся (торможение → город → разгон) — пропускаем. Диагностируем только при стабильном режиме > 10 секунд.

### 4. Quality gate
Если данные "шумные" или классификаторы сломаны (acceleration_state = всё "cruising", road_type = всё "standstill") → показываем "данные ненадёжны, диагностика ограничена" вместо диагноза.

### 5. Контекст двигателя
Не диагностируем на холодном пуске (первые 3 минуты, coolant < 60°C). Многие "аномалии" нормальны при прогреве:
- Повышенные обороты ХХ
- LTFT сдвинут
- Вибрация выше обычной
- Звуки двигателя громче

## Severity Escalation (нарастание серьёзности)

Если проблема не уходит — серьёзность автоматически растёт:

| Время | Уровень | Что показываем |
|-------|---------|---------------|
| Первое срабатывание | ЗАМЕТКА | "Обнаружено: LTFT 12%, мониторим" |
| 3+ дней подряд, confidence > 40% | ПРЕДУПРЕЖДЕНИЕ | "LTFT стабильно 12-14%, стоит проверить" |
| 7+ дней, тренд растёт | ПРОБЛЕМА | "LTFT вырос до 16%, записаться в сервис" |
| 14+ дней, confidence > 70% | СРОЧНО | "LTFT 20%, не откладывайте визит в сервис" |

Если пользователь отклонил → cooldown 7 дней → потом re-escalation если проблема осталась.

Хранится в таблице diagnostic_persistence:
- first_triggered — когда впервые сработало
- consecutive_count — сколько раз подряд
- max_confidence — максимальная уверенность за всё время
- escalation_level — текущий уровень (0=заметка, 1=предупреждение, 2=проблема, 3=срочно)
- user_dismissed_at — когда пользователь отклонил (для cooldown)

## Версионирование весов

### v1 (сейчас, 5 клиентов)
Экспертные веса. Источники: YouTube (2256 комментариев, 22 кейса), CustDev (50 респондентов), профессиональная автодиагностика. Пороги и веса захардкожены.

### v2 (50+ клиентов, через 3-6 месяцев)
Калибровка на данных. Механизм:
- Правило сработало 100 раз, подтверждено 80 → вес растёт
- Правило сработало 50 раз, отклонено 40 → вес падает, порог повышается
- На платформе VW MQB "вибрация Z > 3.0" — ложная тревога в 60% → порог для VW MQB поднимается до 4.0
- Популяционные нормы заменяют хардкодные POPULATION_PRIORS

### v3 (500+ клиентов, через 6-12 месяцев)
Supervised classification. Модель получает features + profile → предсказывает диагноз. Обучается на confirmed diagnoses (user feedback).

### Хранение весов
- Per scope: глобальные → per platform → per brand → per model
- Чем больше данных на конкретном уровне, тем точнее калибровка
- Откат на предыдущую версию если новая хуже (A/B тестирование)
