# Протокол полевых испытаний LLCAR v1.0

**Дата:** 2026-04-16 | **Версия:** 1.0
**Автомобили:** Porsche Cayenne Coupe 2020 (9YA), Li Auto L7 (EREV)
**Локация:** Москва и Московская область
**Формат:** один день, обе машины, один маршрут ~60 км

---

## 1. Цели и задачи

### 1.1 Основные цели

- Верификация 21 диагностического правила подвески/аудио на реальных автомобилях
- Калибровка акселерометра смартфона (сравнение с nRF52810 на подвеске)
- Валидация аудио-детекции (FFT пики, HPSS разделение harmonic/percussive)
- Создание demo-материалов для первых пользователей

### 1.2 Конкретные задачи

- Установить baseline для каждого автомобиля в трёх режимах: idle, city, highway
- Измерить transmissibility ratio (подвеска → кузов): T = RMS_phone / RMS_sensor
- Проверить детекцию wheel hop frequency и его сдвиг при спуске давления шины
- Подтвердить детекцию engine RPM harmonics в аудиоспектре
- Валидировать корреляцию phone vs sensor (Pearson r > 0.80 на highway)
- Измерить реальный EDR (Energy Decay Rate) из raw time-series после speed bump
- Верифицировать proxy-метрики (crest_factor_z, az_range) против прямых измерений
- Собрать ground truth данные для калибровки shadow-правил

### 1.3 Какие правила верифицируются

### 2.2 Расчёт ключевых частот

**Частота вращения колеса при 100 км/ч:**

```
Cayenne: tire_freq = 100 / (3.6 · π · 0.762) = 100 / 8.621 = 11.6 Гц
L7:      tire_freq = 100 / (3.6 · π · 0.728) = 100 / 8.237 = 12.1 Гц
```

**Расчётная частота wheel hop (f_wh = (1/2π)·√(k_t/m_u)):**

| Состояние шины | k_t (Н/м) | Cayenne (m_u=70 кг) | L7 (m_u=62 кг) |
|----------------|-----------|---------------------|----------------|
| Номинальное давление (~2.7 бар) | ~230 000 | **9.1 Гц** | **9.7 Гц** |
| -40% давления (1.6 бар) | ~140 000 | **7.1 Гц** | **7.6 Гц** |
| -55% давления (1.2 бар) | ~100 000 | **6.0 Гц** | **6.4 Гц** |

> Примечание: k_t растёт с D и давлением. Для R21 (Cayenne) k_t_nominal ≈ 230 000 Н/м, для R19 (L7) ≈ 200 000 Н/м. Реальные значения могут отличаться на 15-20%.

**BPFO при 80 км/ч (BPFO_est = 4.0 × wheel_rps):**

```
Cayenne: wheel_rps = 80/(3.6·π·0.762) = 9.3 Гц → BPFO_est = 37.1 Гц
L7:      wheel_rps = 80/(3.6·π·0.728) = 9.7 Гц → BPFO_est = 38.8 Гц
Гармоники Cayenne: 37, 74, 111, 148, 185 Гц
Гармоники L7:      39, 78, 117, 156, 195 Гц
```

**Engine base frequency на idle (Cayenne V6, 750 RPM):**

```
engine_base = 750 / 60 = 12.5 Гц
firing_freq = engine_base × (цил/2) = 12.5 × 3 = 37.5 Гц
Гармоники: 12.5, 25.0, 37.5, 50.0 Гц
```

### 3.2 Размещение смартфона (по ISO 16063)

**Принцип:** Смартфон должен воспринимать ту же вибрацию, что и кузов в точке крепления — без паразитного резонанса крепления.

**Требования:**
- Жёсткое крепление к торпедо (не к стеклу, не к дефлектору воздуха)
- Предпочтительная точка: центр торпедо на жёсткой площадке, вблизи центра масс автомобиля
- Z-axis смартфона — строго вертикально (поперечная ось ±5°)
- Масса смартфона < 10% эффективной массы площадки крепления (выполняется для всех панелей)
- Избегать hand-holding: амплитуда снижается на 15-30% из-за поглощения рукой
- Избегать крепления к сиденью: сиденье имеет собственную демпфирующую характеристику
- После установки: лёгким нажатием проверить, что крепёж не люфтит

**Ориентация осей:**
```
X (ax) — продольная ось автомобиля (вперёд-назад)
Y (ay) — поперечная ось (влево-вправо)
Z (az) — вертикальная ось (вверх-вниз) — ОСНОВНАЯ
```

### 3.3 Установка вибродатчиков nRF52810

**Точки крепления:**

| Датчик | Точка крепления | Что измеряет |
|--------|-----------------|-------------|
| FRONT | Нижний рычаг передней подвески, болт крепления к подрамнику | Неподрессоренная масса: wheel hop, BPFO, дорожный input |
| REAR | Нижний рычаг задней подвески, аналогичная точка | Задняя ось: сравнение с передней, pitch mode |

**Процедура монтажа:**
1. Очистить поверхность рычага в месте установки (обезжиривание спиртом)
2. Приклеить слой эпоксидной ленты 3M VHB как антивибрационную подложку
3. Закрепить датчик хомутами крест-накрест (3 хомута, затяжка до упора без деформации корпуса)
4. Маркером отметить сторону Z-axis — направление строго вертикально вверх
5. Проверить: при нажатии пальцем датчик не смещается и не вибрирует относительно рычага
6. Сопрячь BLE с LLCAR app, убедиться что приходят данные
7. Записать MAC-адрес каждого датчика в протокол: FRONT = ___, REAR = ___

**Критерий правильного монтажа:** статическое az ≈ 9.81 м/с², ax ≈ ay ≈ 0 при неподвижном автомобиле.

### 3.4 Прошивка nRF52810

**SDK и toolchain:**
- nRF5 SDK 17.1.0 или Zephyr RTOS v3.x
- GCC ARM Embedded Toolchain 10.3-2021.10
- nrfjprog v10.x + SEGGER J-Link Software
- nRF Connect for Desktop (для верификации BLE)

**Конфигурация firmware:**
- Sampling rate: **200 Гц** (LIS2DH12 поддерживает до 5376 Гц, но BLE NUS ограничивает)
- BLE profile: Nordic UART Service (NUS)
- Формат пакета: `timestamp (32 bit, мс) | ax (int16, мг) | ay (int16, мг) | az (int16, мг)` = 10 байт
- Буферизация: 10 семплов = 100 байт на BLE уведомление → 20 уведомлений/сек
- Питание: CR2032 (~4-6 ч при 200 Гц) или LiPo 100 мАч (~8-10 ч)
- Масштаб: ±2g (полный диапазон LIS2DH12, LSB = 1 мг)

**Калибровка offset перед поездкой:**
1. Положить датчик на ровную горизонтальную поверхность
2. Записать среднее az за 60 сек: должно быть ≈ 9810 мг (1g)
3. offset_z = az_measured - 9810
4. Записать в файл калибровки: `{sensor_id: "FRONT", offset_z: X, offset_x: Y, offset_y: Z}`
5. Применить коррекцию в ресивере: az_corrected = az_raw - offset_z

### 3.5 Калибровка акселерометра смартфона

**Метод A — статический:**
1. Положить телефон на ровную горизонтальную поверхность
2. Записать az за 2 мин (авто не заведён)
3. Ожидаем: az_mean = 9.81 ± 0.05 м/с²
4. Если отклонение > 0.1 м/с² — проверить ориентацию осей в LLCAR app

**Метод B — температурная коррекция:**
- Чувствительность MEMS акселерометра изменяется ~0.01 м/с² на 10°C
- Записать температуру при калибровке (t_cal) и при каждом эксперименте (t_exp)
- Коррекция: az_corrected = az_measured × (1 + α × (t_exp - t_cal)), α ≈ 0.001/°C
- При разнице температур > 20°C — повторить статическую калибровку

### 3.6 Калибровка микрофона

**Перед началом поездки (на парковке, двигатель не заведён):**
1. Записать 60 сек фонового шума: dominant_amp должен быть < 0.05 (normalised)
2. Проверить, что микрофон не закрыт чехлом или рукой
3. Записать ambient_noise_level в протокол — это baseline для аудио правил
4. При ветре > 15 км/ч: аудиозапись на highway нежелательна (шум ветра +10-20 дБ)

**Примечание:** аудио в LLCAR работает через относительные FFT signatures, а не абсолютный уровень дБ, поэтому абсолютная калибровка микрофона не критична — важна стабильность.

```

## 5. Эксперименты Tier 1: Базовые

### E1: Baseline Calibration

**Цель:** Установить базовую линию всех метрик для каждого автомобиля в трёх режимах (idle, city, highway). Baseline — основа для z-score во всех последующих правилах. Без достоверного baseline z-score метрики недостоверны.

**Правила:** ВСЕ — установка baseline per regime (idle, city, highway). Прежде всего важен для правил с оператором z> (wheel_imbalance, engine_mount, ball_joint, stabilizer_link, damper_energy_decay).

**Автомобили:** Оба

**Подготовка:**
- ✅ Давление шин: проверить ±0.1 бар от OEM спецификации
- ✅ Двигатель прогрет: coolant > 80°C (иначе idle baseline искажён)
- ✅ Смартфон: жёсткий крепёж на торпедо, Z-axis вертикально
- ✅ nRF52810 FRONT и REAR: сопряжены, запись активна
- ✅ OBD: подключён, RPM / speed / coolant / voltage читаются

**Протокол:**

1. **Idle baseline (5 мин):**
   - Двигатель работает (не EV для L7 — RE активен)
   - Автомобиль неподвижен на ровной парковке
   - Запись: az_std, total_vibration, crest_factor_z, dominant_freq, dominant_amp, RPM
   - A/C выключен

2. **City baseline (10 мин):**
   - Движение 30-50 км/ч по ровному городскому асфальту (без кочек и полицейских)
   - Скорость держать константной ±5 км/ч
   - Запись тех же метрик

3. **Highway baseline (5 мин):**
   - 80-100 км/ч на ровном МКАД/ТТК
   - Прямой участок без перестроений
   - Запись тех же метрик

**Ожидаемые значения:**

| Метрика | Cayenne idle | Cayenne city | Cayenne hwy | L7 idle | L7 city | L7 hwy |
|---------|-------------|-------------|------------|---------|---------|--------|

### E16: Front vs Rear Comparison

**Цель:** Проверить симметричность подвески — передняя ось vs задняя. Асимметрия > 30% указывает на неравномерный износ или несимметричную нагрузку.

**Автомобили:** Оба

**Протокол:**

1. Весь маршрут: непрерывная запись FRONT и REAR
2. По окнам 10 сек вычислить az_std для FRONT и REAR
3. asymmetry_ratio = az_std_front / az_std_rear
4. Анализировать по участкам дороги:
   - Трасса: ожидаем ratio ≈ 1.0 ± 0.2
   - Грунтовка: ratio может отличаться из-за разной геометрии подвески
   - Speed bumps: ожидаем ratio близко к 1.0 (симметричная реакция)

**Ожидаемые значения:**

| Участок | Cayenne FRONT/REAR ratio | L7 FRONT/REAR ratio |
|---------|------------------------|---------------------|
| Трасса 80 км/ч | 0.80-1.25 | 0.85-1.20 |
| Город 40 км/ч | 0.80-1.30 | 0.85-1.25 |
| Грунтовка 40 км/ч | 0.75-1.40 | 0.80-1.30 |

**Критерий успешности:**
- ✅ PASS: asymmetry_ratio ∈ [0.7, 1.4] для большинства участков (>80% времени)
- ❌ FAIL: asymmetry_ratio > 1.5 стабильно → одна ось работает существенно интенсивнее → асимметричная нагрузка или неравномерный износ
- 📊 Записать: asymmetry_ratio over time; гистограмма ratio по участкам

### E17: Phone vs Sensor Correlation

**Цель:** Ключевая валидация — подтвердить, что смартфон (PHONE) коррелирует с профессиональным датчиком (FRONT nRF52810) на уровне r > 0.80. Это обоснует использование смартфона как T2-диагностического инструмента.

**Формула:** r = Pearson(az_phone_windows, az_front_windows), окна 500 мс

**Автомобили:** Оба

**Протокол:**

1. Выровнять временные ряды: az_phone и az_front по timestamp (учесть BLE latency ~50 мс)
2. Нарезать на окна 500 мс с overlap 50%
3. Для каждого окна: RMS(az_phone) и RMS(az_front)
4. Вычислить Pearson r по 3 режимам (idle 5 мин, city 10 мин, highway 5 мин):
5. Вычислить gain: K = mean(RMS_front) / mean(RMS_phone)
6. Построить scatter plot: RMS_phone vs RMS_front

**Ожидаемые значения:**

| Режим | Cayenne r | L7 r | Интерпретация |
|-------|----------|------|--------------|
| Idle | 0.3-0.6 | 0.3-0.6 | Слабая корреляция — нормально, мало вибрации |
| City | 0.65-0.80 | 0.65-0.80 | Хорошая — дорожные события видны на обоих |
| Highway | **0.75-0.90** | **0.75-0.90** | Отличная — смартфон надёжен |

**Расчёт K (gain):**
```
K = RMS_front / RMS_phone = 0.85 / 0.15 = 5.7 (типично)
Смартфон занижает амплитуду в ~6× (демпфирование через кузов + крепление)
```

**Критерий успешности:**
- ✅ PASS: r > 0.80 на highway → смартфон валиден как T2-инструмент
- ✅ PASS: r > 0.70 на city
- ❌ FAIL: r < 0.60 на highway → смартфон не улавливает дорожные события (проблема крепления или обработки сигнала)
- 📊 Записать: r и K для 3 режимов × 2 машины; scatter plot; time-series overlay

**Источники ошибок:**
- BLE jitter ±20 мс → временное смещение пиков → r снижается
- Разные OS клокинги (phone vs sensor timestamp) → нужна синхронизация по известному событию (speed bump)
- Крепление смартфона с люфтом → локальный резонанс → r снижается

**Длительность:** весь маршрут (обработка пост-фактум)

## Приложение: Справочные формулы для полевого использования

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
LLCAR ФОРМУЛЫ — ШПАРГАЛКА ДЛЯ ПОЛЯ
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ЧАСТОТЫ:
  tire_freq     = speed / (3.6 · π · D)       [Гц, speed км/ч, D м]
  Cayenne D=0.762: tire_freq = speed / 8.621
  L7 D=0.728:      tire_freq = speed / 8.237

  BPFO_est      = 4.0 × tire_freq              [Гц]
  engine_base   = RPM / 60                     [Гц]
  f_wheel_hop   = (1/2π) · √(k_t / m_u)       [Гц]

АМПЛИТУДЫ:
  crest_factor  = peak / RMS                   [безразм.]
  RMS           = √(avg² + std²)
  az_range      = az_max - az_min              [м/с²]
  z_score       = (value - mean) / std         [σ]

ПОДВЕСКА:
  T (transmissibility)   = RMS_phone / RMS_sensor
  EDR (Energy Decay Rate)= ln(A1/A2) / (2π)
  EDR норма:  > 2.0 (здоровый), < 1.0 (изношенный)
  T    норма:  0.10-0.35 (здоровый), > 0.50 (изношенный)

КОРРЕЛЯЦИЯ:
  r_pearson     = Pearson(az_phone_windows, az_sensor_windows)
  K (gain)      = mean(RMS_sensor) / mean(RMS_phone)
